> **Academic Milestone: Review 1 Prototype (~35% Complete Scope)**

> **Benchmark Subject:** Baseline Auditor vs. SpareSync Rule-Based Reconciliation Engine

---

## 1. Experiment Setup

The objective of this empirical benchmark is to evaluate the operational effectiveness of the **SpareSync Rule-Based Reconciliation Engine** against a standard **Baseline Inventory Auditor** across a simulated multi-hub repair network holding high-value, slow-moving spare components.

### Evaluation Goals
1. Quantify the reduction in unexplained inventory discrepancies when shifting from simple arithmetic variance detection to automated transaction stream analysis.
2. Measure the explanation accuracy of the rule-based engine against known ground-truth failure injections.
3. Assess the computational latency and decision-support quality under operational conditions.

---

## 2. Dataset Description

The evaluation experiment utilizes the reproducible synthetic dataset generated by `src/data_generator.py` (`seed=42`):
- **Total Transactions:** 341 historical transaction records
- **Monitored Inventory Items:** 8 high-value spare parts across 3 regional repair hubs (*Chennai Repair Hub*, *Bangalore Repair Hub*, *Mumbai Repair Hub*)
- **Total Audited Part-Location Nodes:** 24 physical audit checkpoints
- **Transaction Types Modeled:** `RECEIPT`, `PICK`, `TRANSFER_OUT`, `TRANSFER_IN`, `ADJUSTMENT`, `PHYSICAL_COUNT`

## 4. Methodologies Compared

### A. Baseline Method (`src/baseline.py`)
Standard enterprise resource planning (ERP) audit approach:
- Replays transaction credits and debits to compute $\text{System Stock}$.
- Compares against physical count: $\text{Variance} = \text{System Stock} - \text{Physical Stock}$.
- Flags items with $\text{Variance} \ne 0$ as `"Variance Detected"`.
- **Limitation:** Does not analyze transaction history, investigate event sequences, or infer root causes. All variance cases remain 100% unexplained.

### B. Prototype Method: SpareSync Reconciliation Engine (`src/reconciliation_engine.py`)
Rule-based transaction stream investigation:
- Replays chronological event sequences in causal order.
- Applies 4 deterministic rule routines:
  1. **Rule 1 (Unconfirmed Transfers):** Identifies `TRANSFER_OUT` without matching `TRANSFER_IN`.
  2. **Rule 2 (Temporal Duplicates):** Detects identical transactions within a sliding time window ($\le 10$ mins).
  3. **Rule 3 (Network Sync Delays):** Detects un-synchronized edge transactions (`PENDING_SYNC`).
  4. **Rule 4 (Chronological Anomalies):** Detects timestamp inversions violating causal ordering.
- Outputs diagnostic findings, factual evidence trails, explainable confidence scores, and recommended operational recovery actions.

## 5. Evaluation Metrics & Formulas

1. **Total Variance Cases ($V_{total}$):** Number of inventory nodes with non-zero variance or active operational anomalies.
2. **Correctly Explained Cases ($V_{explained}$):** Number of variance cases where the diagnosed root cause matches the ground-truth label.
3. **Unexplained Cases ($V_{unexplained} = V_{total} - V_{explained}$):** Cases left unresolved or classified as generic discrepancy.
4. **Explanation Accuracy:**
   $$\text{Explanation Accuracy} = \frac{V_{explained}}{V_{total}} \times 100\%$$
5. **Unexplained Variance Rate:**
   $$\text{Unexplained Variance Rate} = \frac{V_{unexplained}}{V_{total}} \times 100\%$$
6. **Variance Reduction:**
   $$\text{Variance Reduction} = \text{Baseline Unexplained Rate} - \text{Prototype Unexplained Rate}$$
7. **Processing Time:** Execution duration of the complete reconciliation pass in milliseconds.

## 7. Error Analysis & Edge Cases

The experimental evaluation highlighted key boundary conditions where deterministic rule-based systems face challenges:

1. **Endpoint Ambiguity in Inverted Transfers:**
   In Scenario 4 (`SP-004`), the timestamp inversion between Mumbai (source) and Bangalore (destination) was flagged at both hubs. While Bangalore (the receiving node) matched the ground truth label, Mumbai was also flagged as anomalous because it was a party to the inverted transaction. In production, bi-directional transfer link deduplication is recommended.
2. **Multiple Simultaneous Errors:**
   If a technician performs an offline pick during a network outage and simultaneously enters a clerical count error during cycle counting, composite errors may mask individual rule signatures.
3. **Delayed Synchronization Windows:**
   If offline edge devices remain disconnected beyond the standard reconciliation window, central systems may prematurely classify discrepancies as shrinkage before synchronization occurs.
4. **Missing Multi-System Logs:**
   If transactions occur in external 3PL carrier systems without API integration, the engine cannot inspect external milestones.

## 8. Limitations & Future Extensions

- **Current Prototype Scope:** The Review 1 prototype utilizes an explainable, deterministic rule-based engine, which provides full transparency and immediate auditability but lacks probabilistic pattern recognition.
- **Review 2 / Future Roadmap:**
  1. Introduce sequence neural models (LSTM / Transformer) to predict expected transaction flows and score anomaly likelihoods dynamically.
  2. Implement automated write-back connectors to post authorized journal entries directly into ERP databases.
  3. Expand the multi-criteria trade-off model (Cost, Time, CO₂ Emissions, Reliability) to evaluate competing recovery decisions.
